## 1. Продукт

«Сходим» — афиша Петербурга и компания на вечер. Пользователь смахивает карточки событий (лайк или пропуск), отмечает «Хочу пойти», видит, кто ещё идёт на тот же сеанс, приглашает человека и договаривается с ним в чате.

**Аудитория:** студенты и молодые специалисты Петербурга примерно 18–30 лет, которым хочется выбраться на событие, но не с кем. Отсюда яркий плакатный стиль, свайп как основной жест и акцент на «кто ещё идёт».

**Стек:**

| Часть | Технологии |
|---|---|
| База данных | PostgreSQL 17 (на helios та версия, что стоит на сервере), pl/pgsql |
| Бэкенд | Java 17, Spring Boot 3.3, Spring Security + JWT, JdbcTemplate, springdoc (Swagger) |
| Фронтенд | React 18, TypeScript, Vite, React Router, TanStack Query, Framer Motion, lucide-react |
| Тесты | JUnit 5 + MockMvc, Playwright, SQL-проверки |
| Сборка и выкладка | Maven (собирает и фронтенд), bash-скрипты, GitHub Actions |
| Отчёт | python-docx, docxcompose, PlantUML |

Один JAR отдаёт и REST API (`/api/v1/**`), и собранный React: адреса без `/api` возвращают `index.html` (`web/SpaConfig.java`), поэтому прямые ссылки вроде `/events/27` открываются сразу.

## 3. Архитектура

Классическая трёхуровневая схема с одним жёстким правилом этапа 3: **все запросы к данным живут в функциях БД**. Java-слой хранения только передаёт параметры в pl/pgsql-функции и переводит строки результата в записи.

```
React (frontend/src)
   │  fetch /api/v1/...  с JWT в заголовке Authorization
   ▼
web/        контроллеры REST, обработка ошибок, отдача SPA
service/    бизнес-логика, импорт афиши, склейка дублей
repository/ JdbcTemplate → SELECT * FROM <функция>(...)
   ▼
PostgreSQL: таблицы, триггеры целостности, функции экранов и импорта
```

Пакеты бэкенда (`src/main/java/ru/ifmo/skhodim`):

| Пакет | Что внутри |
|---|---|
| `web` | `AuthController`, `EventController`, `MeController`, `CompanionController`, `SocialController`, `AdminController`, `HealthController`, `ApiExceptionHandler`, `ApiMessages` (перевод ошибок на русский), `SpaConfig`, `OpenApiConfig` |
| `service` | `UserService`, `CatalogService`, `ReactionService`, `CompanionService`, `FeedbackService`, `ModerationService`, `PresentationService`, `ShareCardService`, `ImportService`, `MarkupSource`, `KassirSource`, `AfishaSource` |
| `repository` | По репозиторию на область, `PresentationRepository` для экранов этапа 4, `ImportRepository` для импорта и склейки |
| `security` | `SecurityConfig`, `JwtAuthFilter`, `JwtService`, `AuthFacade`, `SkhodimPrincipal` |
| `scheduler` | `RequestExpirationScheduler` (просрочка заявок), `CatalogRefreshScheduler` (обновление афиши раз в сутки) |
| `domain` | Записи предметной области и `Views` с ответами экранов |

Диаграмма классов: [docs/architecture.png](architecture.png), исходник [docs/architecture.puml](architecture.puml).

### 4.2. Целостность

Ограничения и триггеры не дают сломать данные даже прямыми запросами в обход приложения.

- **Ключевые ограничения:** уникальный email без учёта регистра, одно открытое «хочу пойти» на человека и сеанс, одна заявка на пару людей и сеанс (`user_low`, `user_high`), одна открытая жалоба автора на одну цель, один отзыв с оценкой на человека и событие, один запущенный импорт на источник.
- **Триггеры** (`sql/02_logic.sql`):

| Триггер | Что проверяет или делает |
|---|---|
| `trg_intention_period_overlap` | Периоды «хочу пойти» одного намерения не пересекаются |
| `trg_intention_close_cancels_requests` | Снял «хочу пойти» — его ожидающие заявки на этот сеанс отменяются |
| `trg_companion_request_check` | Заявку можно отправить, только если оба идут на этот сеанс и он ещё не прошёл |
| `trg_request_status_transition`, `trg_request_status` | Допустимые переходы статуса заявки; при принятии создаётся диалог |
| `trg_message_notify` | Новое сообщение создаёт уведомление собеседнику |
| `trg_review_check` | Отзыв с оценкой только после сеанса и только от того, кто на него шёл |
| `trg_protect_reviewed_session` | Расписание сеанса с отзывами менять нельзя |
| `trg_ban_cancels_requests` | Блокировка пользователя отменяет его ожидающие заявки |
| `trg_hide_cancels_requests`, `trg_session_cancel_requests` | Скрытие события или отмена сеанса отменяют ожидающие заявки |
| `trg_lock_<таблица>` | Общая блокировка (`lock_shared_state`) на прямые изменения 14 таблиц, чтобы параллельные запросы не обходили проверки триггеров |

## 5. Бэкенд

### 5.1. Безопасность

- **Вход:** email и пароль, пароли хранятся в BCrypt. В ответ выдаётся JWT на 24 часа, фронтенд хранит его в `localStorage`.
- **Роли:** `USER` и `MODERATOR`. Всё под `/api/v1/admin/**` доступно только модератору. Лента, поиск и карточка события открыты гостям, остальное требует входа.
- **Неверный или просроченный токен** не ломает публичные страницы: запрос просто считается гостевым.
- **Блокировка действует сразу:** заблокированный пользователь теряет доступ даже с ещё действующим токеном.
- **Чужие данные недоступны:** уведомления, заявки и чаты проверяют, что принадлежат текущему пользователю (исправлена найденная уязвимость IDOR, см. раздел 13).

### 5.2. Ошибки

`ApiExceptionHandler` превращает исключения в JSON вида `{"error": "..."}` с нужным HTTP-статусом. `ApiMessages` переводит внутренние сообщения (в том числе сообщения триггеров БД) на понятный русский: «Выберите от 3 до 5 интересов», «Эту пару уже рассмотрели», «Не удалось получить афишу с Кассир.ру. Каталог не изменён». Текст ошибок базы наружу не уходит: для неизвестной ошибки показывается общее «Не получилось выполнить действие».

### 5.3. REST API

### 5.4. Фоновые задачи

- `RequestExpirationScheduler` раз в минуту вызывает `expire_requests()`: заявки на прошедшие сеансы закрываются. Триггер сам по времени не срабатывает, поэтому нужен планировщик.
- `CatalogRefreshScheduler` раз в сутки в 06:00 по Москве обновляет афишу из Кассир.ру и Афиши.ру. Расписание задаётся в `app.catalog.refresh-cron`, значение `-` отключает обновление (так сделано в тестах).

## 6. Откуда берутся события

В рабочей базе **нет выдуманных событий**: каталог заполняется только импортом. Синтетические 1000 событий этапа 2 остались лишь в тестовой базе.

### 6.1. KudaGo: почему не получилось

Изначально события шли из публичного API KudaGo. На этапе 4 выяснилось, что он отвечает 403 на любой автоматический запрос: с домашнего компьютера (с VPN и без) и с helios. Причина: перед всем сайтом стоит JavaScript-проверка «Проверка безопасности», а `robots.txt` запрещает обход `/public-api`. Журнал на helios показал 403 ещё с 27 октября, то есть настоящие события через API не приходили ни разу. Раньше это скрывалось: импорт при ошибке молча подставлял встроенный файл с двумя тестовыми событиями.

Что сделано:

- Подстановка тестового файла убрана. Сбой виден модератору в истории импорта, а каталог остаётся прежним (требование NFR-6).
- Обход защиты (подмена браузерных заголовков, прохождение проверки программой) **не применялся и не будет**.
- Кнопка KudaGo и загрузка сохранённой выгрузки JSON оставлены: если доступ вернётся, они заработают без изменений.

### 6.2. Поиск замены

Проверено 10 сайтов и 12 вариантов API: Timepad, VK, PRO.Культура.РФ, Radario, Ticketscloud, партнёрские выгрузки Ticketland и Афиши, Яндекс Афиша, Bandsintown, Songkick, Ticketmaster и другие. Самостоятельно подключаемого официального API с концертами Петербурга не нашлось: везде нужен договор, токен или одобрение. Ближайший официальный вариант — Timepad, для него нужен токен с учётной записи.

Зато два крупных сайта продажи билетов публикуют на страницах **разметку schema.org** для поисковиков: название, даты, площадку, цену, постер, ссылку на покупку. Её и читает импорт.

### 6.3. Как читается разметка

Общий код в `service/MarkupSource.java`, у каждого сайта свой наследник:

| | Кассир.ру (`KassirSource`) | Афиша.ру (`AfishaSource`) |
|---|---|---|
| Страницы | 11 разделов и до 80 страниц площадок | 14 разделов и до 40 страниц площадок |
| Время | В разметке стоит `+00:00`, а на странице то же время по Петербургу. Читается как время Москвы | Часовой пояс указан верно, читается как есть |
| Категория | По первой части адреса (`koncert`, `teatr`, `shou`…) | По типу события (`MusicEvent`, `TheaterEvent`…); раздел «Детям» добавляет категорию «Детям» |
| Постеры | Около 448 px | До 2220 px |
| Описания | Нет | У части событий |
| Ранг постеров `media_rank` | 1 | 2 |

Что делает разбор:

- **Одно событие на разные даты** собирается в одну запись с несколькими сеансами. Ключ сеанса — фрагмент адреса или время начала, а не номер в списке: порядок дат на страницах меняется.
- **Отбрасываются** прошедшие и отменённые события, абонементы и подарочные сертификаты.
- **Метро** достаётся из адреса в любом из встречающихся форматов: «(метро X)», «ст.м. "X"», «м. X».
- **HTML в описаниях** раскодируется и очищается, в том числе экранированные теги вида `&lt;p&gt;`.
- **Слишком длинный адрес события** (до 128 символов при колонке на 100) сокращается с хешем на конце, чтобы id оставался уникальным и стабильным.
- **Площадка «Неизвестно»** на Афише.ру не заводится.

Правила вежливого сбора:

- читаются только страницы, разрешённые `robots.txt` (проверено для всех используемых путей);
- между запросами пауза 0,5 секунды;
- клиент представляется честно: `skhodim-course/1.0`;
- на страницы площадок ходим только по адресам самого сайта;
- если сайт откажет, импорт честно сообщит о сбое, а каталог не изменится.

### 6.4. Запуск импорта

- **Кнопки модератора:** «Обновить афишу с Кассир.ру» (около 3,5 минуты), «Обновить афишу с Афиши.ру» (около 1,5 минуты), «Загрузить выгрузку JSON». Живой синхронизации с KudaGo нет: сайт закрыт проверкой на бота.
- **Автоматически** раз в сутки, см. раздел 5.4.
- **Запись идемпотентна:** повторный импорт обновляет события, а не создаёт новые. Каждый запуск пишется в `import_run`, ошибки отдельных событий в `import_error`; история видна на вкладке «Импорт афиши».

На локальной проверке Кассир дал 832 события, Афиша.ру 1089. После склейки в каталоге 1734 события на 237 площадках.

## 7. Склейка дублей

Около пятой части событий Афиши.ру уже есть в каталоге из Кассира, только записаны иначе: «ХАСКИ» и «Хаски», «СК Юбилейный» и «СК «Юбилейный»», «Группа «ПЕЛАГЕЯ»» и «Пелагея». Без склейки в свайпе каждое такое событие попадалось бы дважды. Всё сделано в `sql/11_sources.sql`.

### 7.1. Одно событие, несколько источников

- `event_link` хранит данные каждого источника: название, описание, постер, цену, ссылки.
- `refresh_event` собирает из них поля самого события: **минимальную цену**, самое полное **настоящее описание**, **название и постер** у источника с лучшим `media_rank` (то есть с Афиши.ру), ссылки у основного источника. Если описания нет, подставляется название, и интерфейс такое «описание» не показывает.
- `event_offers` отдаёт список «где купить», который виден на странице события: «Кассир.ру от 600 ₽ · Афиша.ру от 600 ₽».
- **Площадки** тоже не дублируются: `find_place_alias` находит площадку другого источника с теми же словами в названии.
- `upsert_event_session` не создаёт второй сеанс на то же время, если его уже привёз другой источник.

### 7.2. Как находятся пары

`find_duplicate_pairs` сравнивает события, у которых есть сеансы в один день:

- **Название** превращается в набор слов без регистра, кавычек, пометок в скобках, служебных слов («билеты», «премьера») и жанровых («группа», «спектакль», «мюзикл», «концерт»). Поэтому «Лолита (ЛОЖИ)» и «Лолита.» дают одно и то же.
- **Площадка** — набор слов без города и «им.», но **тип площадки сохраняется**: иначе «ДК Ленсовета» совпал бы с «Театром им. Ленсовета».
- **Регистр** приводится вручную, а не через `lower()`: у `lower()` поведение для кириллицы зависит от локали базы, а она на серверах разная.

| Решение | Условие |
|---|---|
| Склеить автоматически | Сеансы в пределах 30 минут, названия совпадают, площадка совпадает или неизвестна |
| Склеить автоматически | Сеансы в пределах 30 минут, одно название целиком входит в другое, сходство названий не меньше 0,6, площадка совпадает |
| Склеить автоматически | В тот же день в другое время, названия совпадают, площадка совпадает (это другой сеанс того же показа) |
| Отдать модератору | Источники разные, площадка совпадает, названия похожи, но не наверняка |
| Не трогать | Всё остальное, а также пары, которые модератор уже пометил разными |

Правила подобраны на живых данных, и проверка поймала две ловушки:

- **Гастрольный стендап.** «Стендап по-Женски» в один вечер идёт в двух разных барах, поэтому площадка должна совпасть целиком.
- **Разные билеты одного сайта.** «Два мастер-класса» и «Комбо: экскурсия + два мастер-класса», фан-зона на концерте — это намеренно разные позиции Кассира. Поэтому внутри одного источника пары модератору не показываются, а порог сходства для автосклейки высокий.

### 7.3. Что происходит при склейке

`merge_events(оставить, убрать)` переносит на оставшееся событие:

- сеансы (повтор на то же время удаляется, если с ним ничего не делали);
- лайки, категории, теги;
- комментарии;
- жалобы (повторная открытая жалоба того же автора закрывается);
- источники (`event_link`).

Затем удаляет лишнее событие и пересобирает поля оставшегося. Событие, у которого есть отзывы с оценкой, не склеивается: такие отзывы привязаны к расписанию.

`resolve_duplicates` запускается после каждого импорта. Уверенные пары он склеивает, сомнительные кладёт в очередь `event_duplicate`. Цепочки вида «А похоже на Б, Б похоже на В» сходятся за несколько проходов, их максимум 10. Остаётся событие, с которым люди уже что-то делали, иначе более раннее.

### 7.4. Решение модератора

Вкладка «Модерация → Дубли» показывает обе стороны пары: постер, название, источник, площадку и ближайший сеанс. Модератор нажимает «Оставить это» у нужного события или «Это разные события»; второе решение запоминается, и пара больше не предлагается.

### 8.2. Внешний вид

Макет был чёрно-белым наброском, поэтому стиль задан заново под аудиторию:

- **Шрифты:** плакатный Dela Gothic One для заголовков, округлый Rubik для текста. Оба поддерживают кириллицу и поставляются вместе с приложением, без внешних запросов.
- **Цвета:** глубокий фиолетовый, лайм, розовый и жёлтый. У каждой категории свой цвет и узор плаката для событий без постера.
- **Тема:** светлая и тёмная, выбор сохраняется. Движение отключается по системной настройке «уменьшить движение».

Стиль менялся по замечаниям: сначала ближе к Figma, затем «громче и веселее», затем карточка свайпа уменьшена до пропорции 3:4.

### 8.3. Телефон и компьютер

- **Телефон:** нижняя панель из четырёх разделов (Свайп, Соцсеть, Список, Профиль), карточки в одну колонку.
- **Компьютер:** навигация в шапке, как на сайтах афиш: разделы, поле поиска, приглашения, чаты и уведомления со счётчиками, аватар. Содержимое стоит по центру на всю ширину (до 1200 px). Главная показывает крупную карточку слева, а справа заголовок, фильтры и сетку «Дальше в ленте» из шести событий. Чат занимает всю высоту под шапкой.
- **Узкое окно ноутбука (900–1240 px):** у разделов скрываются иконки, сетка «Дальше в ленте» становится двухколоночной.
- **Кнопка «←»** на компьютере убрана у разделов, которые и так есть в шапке.

### 8.4. Свайп без мелькания

Карточки устроены как **стопка из трёх**: верхняя, видимая под ней и ещё одна в запасе. Нижняя карточка сама становится верхней, тем же элементом и с уже загруженным постером. Улетающая карточка всегда идёт поверх остальных. Постеры следующих пяти событий загружаются заранее, по одному и с низким приоритетом, чтобы не отнимать канал у постера на экране. Незагруженный постер плавно проявляется на тёмном фоне.

До этого исправления при смене карточки на долю секунды смешивались три постера и мелькала цветная заливка. Причина найдена по покадровой записи, проверка повторена на медленном интернете.

### 8.5. Выравнивание карточек

В рядах карточек кнопки, статусы, цены и даты прижаты к низу, а имена — к верху. Даже если у соседа название в две строки, элементы в ряду стоят на одной линии. Это проверено скриптом на всех экранах при ширине 1440, 1000 и 390 px.

## 11. Выкладка на helios и CI/CD

- **Где живёт:** приложение работает на helios в отдельной папке `~/skhodim` и слушает только `127.0.0.1:18080`. Снаружи оно открыто по адресу <https://hearty-heron-4014.a.tuna.free> через туннель Tuna, запущенный на helios. Без туннеля доступ только через SSH. База `studs`, хост `pg`, личная схема пользователя. Профиль Spring `helios` берёт схему и пароль из переменных окружения, в репозитории их нет.
- **`deploy/deploy.sh`** (запускается на своём компьютере) собирает JAR, загружает его и скрипты, применяет миграции и перезапускает приложение.
- **`deploy/release.sh`** (запускается на сервере) кладёт версию в `releases/<время>`, останавливает только свой процесс по pid-файлу, запускает новую и ждёт ответа `/api/v1/health`. При сбое **автоматически возвращает прошлую версию**; это проверено на заведомо сломанном JAR.
- **`deploy/db.sh`** выполняет действия с базой на сервере:
  - `check` показывает таблицы проекта и всё остальное в схеме;
  - `backup` сохраняет копию;
  - `migrate` применяет `08` и `11`;
  - `reset` пересоздаёт только таблицы проекта, сначала показав список, спросив подтверждение и сохранив копию;
  - `activity` добавляет демо-активность.

  Скрипты **ничего лишнего на helios не удаляют**: `90_drop_schema.sql` не используется.
- **`deploy/tunnel.sh`** (на сервере) поднимает туннель Tuna, если тот не работает (`start`), останавливает его (`stop`) и показывает состояние (`status`). Если tuna упадёт, `daemon` перезапустит её. `deploy.sh` вызывает `start` после каждой выкладки. Почему Tuna: helios выпускает наружу только порт 443, а ngrok не принимает подключения с российских IP.
- **`.github/workflows/ci.yml`** на каждое изменение собирает проект и прогоняет SQL-проверки, тесты бэкенда и браузерные тесты. Выкладка идёт из `main` или запускается вручную; ключи хранятся в секретах окружения `helios`. После выкладки CI проверяет `/api/v1/health` по публичному адресу с сервера GitHub.

**Текущее состояние:** версия этапа 4 выложена на helios через GitHub Actions, сайт открыт по публичному адресу. Импорт на helios ещё не проверен: после него нужно убедиться в истории запусков, что сайты-источники доступны с сервера. После перезагрузки helios туннель нужно запустить вручную: `sh ~/skhodim/incoming/deploy/tunnel.sh start`.

## 13. Найденные и исправленные ошибки

Всё ниже найдено при проверках этапа 4 и исправлено, многое закреплено тестами.

**Данные и безопасность:**

- **Скрытый сбой импорта.** При ошибке KudaGo подставлялся тестовый файл с двумя событиями, а модератор видел «успешно».
- **IDOR в уведомлениях.** Можно было пометить прочитанным чужое уведомление по id.
- **Утечка текста ошибок БД** в ответы API.
- **Несовпадение цели жалобы и действия.** Жалоба на пользователя могла скрыть событие с тем же числовым id.
- **Блокировка начинала действовать** только после истечения токена.
- **`get_messages`** возвращал самые старые сообщения вместо последних.
- **Выбор сеанса** для заявки мог взять уже прошедший.
- **Время Кассира** сдвигалось на 3 часа (разметка помечена как UTC, а время местное).
- **Экранированный HTML** в описаниях Афиши.ру не очищался.
- **Хрупкий тест** ломался, когда истекали даты в тестовых данных.

**Интерфейс:**

- **Мелькание** нескольких постеров при свайпе.
- **Прыгающая вёрстка** при улёте карточки.
- **Разъезжающиеся кнопки и цены** в соседних карточках.

## 14. Ограничения и что осталось

**Ограничения источников:**

- **Нет официального API.** Источники событий — публичная разметка сайтов. Если её поменяют, импорт сообщит о сбое.
- **Условия использования** проверены только поиском по ключевым словам. Для учебного проекта этого достаточно, но вне учёбы использование данных нужно согласовать с Кассир.ру и Афишей.ру.
- **Описания** есть только у части событий (около 230 из 1734), метро указано лишь у части площадок.
- **Постеры Афиши.ру крупные** (до 2220 px): на медленном интернете они грузятся дольше, зато не мыльные на компьютере.

**Демо-данные:** участники, их отметки, комментарии и переписка вымышленные. Это демо-учётки `demo1@example.org` … `demo9@example.org` и модератор `demo100@example.org`, пароль у всех `Demo12345!`.

**Что осталось сделать:**

1. **Проверить импорт на helios:** кнопками модератора или дождаться запуска в 06:00.
2. **Слить `stage-4` в `main`,** чтобы выкладка шла автоматически при каждом изменении `main`.
3. **Подключить Timepad**, когда будет токен: это официальный API и лекции, стендап, небольшие концерты.
4. **Сделать презентацию:** её требует задание, в проект она не входит.
